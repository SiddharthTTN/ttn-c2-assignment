# Error handling

Controllers map validation failures to 400, missing resources to 404, invalid state transitions and optimistic-lock failures from PATCH, comment, or status writes to 409, and confirmed embedding/chat dependency failures to 503. Database, decoding, and programming failures are not relabeled as model outages; they reach the sanitized generic 500 handler. Every client error uses `{error, details[]}` and carries or creates an `X-Correlation-ID`. Unexpected failures return a generic 500 message without stack traces or provider details.

Ticket writes remain committed when asynchronous post-commit knowledge refresh fails; the ticket stays `PENDING`, stale chunks are excluded from asks, and startup or a scheduled worker retries only when `knowledge_next_retry_at` becomes due using capped delays of 5 seconds, 30 seconds, and 5 minutes. Failure recording is ignored when its captured knowledge version is stale. The complete ask pipeline has one 7.5-second deadline; deadline expiry or executor saturation returns 503. Model generation is not automatically retried to avoid duplicate cost and latency. Malformed or structurally invalid model JSON fails closed to the fixed no-match response; raw model prose is never returned. The UI presents server error meaning next to the affected action and preserves entered form values; ask validation failures appear inline without a duplicate global alert.
